最終更新: 2026-08-19

> 前提の断り書き: このドキュメントを書いた時点で、GA4の実データ(セッション数・
> 離脱率・検索クエリ)には接続していません。したがってここでの分析は「サイトの構造から
> 論理的に導けるボトルネック」であって、実測ではありません。
> **だからこそ最初にやるべきは計測です。** 1章がそれで、2章以降は
> 計測が返ってきたときに打てる手を、効きそうな順に並べたものです。

| 観点 | 判明していた課題 | 今回の対応 |

## 1. 体験フローを、GA4で見えるようにする

### 1.1 なぜ今まで見えなかったのか

MYOURISCOPEは **ハッシュルーティングのSPA + 静的LP** という二層構造です。GA4に入っていたのは:

- LP側: `gtag("config", ...)` の自動 `page_view` のみ
- アプリ側: ビュー切り替えごとの `page_view`(`app.js` の `gaPageView`)のみ

つまりGA4には「ページが表示された」しか届いていませんでした。この状態でわかるのは
**セッション数・直帰率・ページ別滞在**まで。わからないのは:

- LPを読んだ人のうち、何%がアプリに渡ったのか
- アプリに渡った人のうち、何%が生年月日を入れたのか
- 生年月日を入れた人のうち、何%が結果まで到達したのか
- どの占術のフォームがいちばん落ちるのか
- LPの記事は最後まで読まれているのか、FVで閉じられているのか

改善は「どこが漏れているか」がわからないと打てません。ここを埋めるのが最初の一手です。

### 1.2 入れたイベント

すべて `js/analytics.js` を通り、下記の**共通パラメータ**が自動で付きます。

| 共通パラメータ | 値の例 | 何がわかるか |
|---|---|---|
| `page_kind` | `app` / `lp_divination` / `lp_sign` / `lp_tarot_card` / `lp_aisho_pair` / `lp_kyusei` / `hub_*` | ページ種別ごとの束で比較できる(78枚のカードページを1行で見る等) |
| `page_id` | `today` / `seiza_leo` / `aisho_seiza_aries-leo` | 個別ページの識別 |
| `entry_page` / `entry_kind` | セッション最初の入口 | **LP→アプリの越境を1本の線にする鍵** |
| `visitor` | `new` / `returning` | 新規と再訪で挙動を分ける |
| `has_profile` | `yes` / `no` | 生年月日を入れ済みか(=初回体験か再訪か) |

送っているイベント:

| イベント | 発火点 | 主なパラメータ |
|---|---|---|
| `lp_view` | LP表示 | `lp_id`, `lp_kind` |
| `scroll_depth` | 25/50/75/90%到達 | `percent` |
| `dwell` | 離脱直前(1回) | `seconds`, `bucket`, `max_scroll` |
| `cta_click` | アプリ本体へ渡るリンク | `link_group`(cta/related/footer/header_nav/breadcrumb/card_nav/in_article) |
| `internal_link_click` | サイト内リンク | 同上 |
| `faq_open` | FAQを開いた | `question` |
| `outbound_click` | 外部リンク | `link_url` |
| `lp_form_view` / `lp_form_start` / `lp_form_submit` / `lp_form_error` | LP直置きフォーム | `to`, `state`, `from` |
| `lp_handoff` | LPから引き継いでアプリ着地 | `to`, `has_profile` |
| `reading_form_view` / `reading_submit` / `reading_view` | 占術のファネル3点 | `reading`(today/western/eastern/aisho/integrated), `first_time` |
| `tarot_ritual_start` / `tarot_ritual_complete` | タロットの儀式 | `spread`, `cards`, `deep_shuffle`, `genre` |
| `share_click` | 結果のコピー | `method`, `label` |

**個人情報は送りません。** 生年月日も名前も送らず、「入力済みか否か」までです
(`docs/PRODUCT.md` の「データは端末の中だけ」という思想を計測でも崩さない)。

### 1.3 GA4側でやること(コードでは完結しない)

1. **カスタムディメンションを登録する**(管理 → データの表示 → カスタム定義)。
   イベントスコープで最低この7つ:
   `page_kind` / `page_id` / `entry_page` / `visitor` / `has_profile` / `reading` / `link_group`
   *登録しないとレポートで使えません。登録日以降のデータにしか効かないので、最初にやること。*
2. **ユーザースコープ**で `visitor_type` / `profile_saved` / `streak_bucket` を登録。
3. **キーイベント(旧コンバージョン)** に指定するもの:
   `reading_view`(結果到達=このサービスの成功)、`lp_form_submit`、`tarot_ritual_complete`。
4. **目標到達プロセスの探索**を2本作る:
   - 検索流入ファネル: `lp_view` → `lp_form_start` → `lp_form_submit` → `lp_handoff` → `reading_view`
   - アプリ内ファネル: `reading_form_view` → `reading_submit` → `reading_view`
   ここに `entry_page` を内訳ディメンションで刺すと、**「どのLPから来た人がいちばん結果まで行くか」**が
   1画面で出ます。これがLPの優先順位を決める数字になります。
5. **Search Console を GA4 に連携**する。GA4単体では検索クエリが見えません。
   4章のキーワード判断は、Search Consoleの「表示回数はあるがCTRが低いクエリ」を見て回します。

### 1.4 この計測で最初に見るべき3つの数字

| 見る数字 | 出し方 | 良くない場合に打つ手 |
|---|---|---|
| **LP→結果の到達率** | `reading_view` ÷ `lp_view`(`entry_page` 別) | 低いLPは、記事が長すぎるかCTAが遠い。FVフォームの位置を上げる |
| **フォーム着手率** | `lp_form_start` ÷ `lp_form_view` | 低ければ、フォームの見た目が「入力させられる感」になっている。文言と初期値を見直す |
| **記事の読了** | `scroll_depth(90)` ÷ `lp_view` | 極端に低いページは、検索意図とタイトルがずれている。h1と冒頭2段落を検索クエリに寄せる |

## 2. 体験フローそのものの改善

### 2.1 今回入れた: LPの入口に生年月日フォームを直置き

**旧**: LPを読む → CTAを押す → 別ページに遷移 → アプリのフォームを見る → 生年月日を入れる → 結果
**新**: LPで生年月日を入れる → 遷移 → 結果

検索から来た人にとって、CTAを押した先にもう一枚フォームがあるのは「まだ終わらないのか」という体験です。
LPで先に入力させて `fortuna:profile` に書き、アプリ側は `?ms=go#western` を受けて**到着と同時に自動で結果まで進める**
ようにしました(`app.js` の `handoffFromLp`)。

- 対象は生年月日が要る行き先だけ(`#today` `#western` `#eastern` `#integrated`)。
  タロットLPは入力が不要、相性LPはふたり分必要なので対象外。
- 再訪者には入力欄を出さず「記憶している生年月日 1990年5月14日 → 観る」の**1タップ**にしています。
- JSが動かない環境では従来のリンクCTAがそのまま残ります(プログレッシブエンハンスメント)。

### 2.2 次に効きそうな順(計測が返ってきてから判断する)

| 優先 | 施策 | 狙い | 判断に使う数字 |
|---|---|---|---|
| 高 | **相性LPにもふたり分のフォームを置く** | 相性は検索需要が大きいのに、いま唯一フォーム直置きの対象外 | `/aisho/` の `cta_click` → `reading_view(aisho)` の落差 |
| 高 | **結果画面から次の占術への橋渡しを1本に絞る** | いま結果の下は情報量が多い。次の一手が複数あると誰も押さない | 結果ページの `internal_link_click` の分散度 |
| 中 | **タロットLPに「今日の一枚」の即引き導線** | タロットは生年月日不要 = 最短で価値に触れられる面。いまは1クッション置いている | `lp_tarot_card` からの `tarot_ritual_start` 率 |
| 中 | **78枚のカードページから、そのカードで引ける導線** | ロングテール流入の受け皿が「読んで終わり」になっている | `lp_tarot_card` の `dwell` と `cta_click` の比 |
| 中 | **初回の観測演出をスキップ可能にする** | 演出は世界観だが、検索から来た初回訪問者には待ち時間 | `reading_submit` → `reading_view` の間の離脱 |
| 低 | **PWA追加の訴求タイミング** | 連続日数が伸びた人にだけ出す | `streak_bucket` 別の再訪率 |

## 3. 検索ワードの攻略 — 考え方

このサイトは**サーバーを持たない静的サイト**です。だから検索対策の打ち手は次の3つに限られます。

1. **面を増やす** — 検索クエリごとに専用の静的ページを作る(ロングテールの受け皿)
2. **面の質を上げる** — 各ページが検索意図に本当に答えているか(タイトル・h1・冒頭・FAQ)
3. **面をつなぐ** — 内部リンクでクローラの巡回と、ユーザーの回遊を作る

そして重要なのが、**ページは「データから生成する」**という既存の方針です。
タロット78枚のページが `js/data.js` から生成されているのと同じく、今回追加した相性・九星も
`scripts/gen-pages.mjs` が `data.js` / `fortune.js` を評価して本文を作ります。
手打ちしないので、**本体アプリの判定とLPの記述が食い違うことが原理的に起きません**。

### 3.1 キーワードクラスタの地図

| クラスタ | 検索の型 | 現状 | 状態 |
|---|---|---|---|
| 占術の一般名 | 「タロット占い」「四柱推命」「ホロスコープ」 | `/tarot/` `/shichusuimei/` `/horoscope/` ほか6本 | 既存 |
| 星座の基礎 | 「しし座 性格」「おうし座 期間」 | `/seiza/{sign}/` 12本 | 既存 |
| タロット札の意味 | 「塔 タロット 意味」「女教皇 逆位置」 | `/tarot/cards/{slug}/` 78本 | 既存 |
| **星座 × 星座の相性** | 「おうし座 さそり座 相性」 | `/aisho/seiza/{a}-{b}/` **78本** | **今回追加** |
| **九星の本命星** | 「一白水星 性格」「三碧木星 相性」「吉方位」 | `/kyusei/{star}/` **9本** | **今回追加** |
| 今日の運勢 × 星座 | 「しし座 今日の運勢」 | なし | 4.1 参照(要・日次ビルド) |
| 四柱推命の日主 | 「甲 日主 性格」「通変星 偏官」 | なし | 4.2 参照 |
| 誕生日占い | 「3月14日生まれ 性格」 | なし | 4.3 参照 |
| 暦・イベント | 「2026 新月 満月」「水星逆行 いつ」 | なし | 4.4 参照 |

### 3.2 今回追加した2クラスタの設計意図

**星座相性(78ページ)** — `/aisho/seiza/{a}-{b}/`

- 組み合わせは**順不同で78通り**にしました。144通り(順序あり)にすると
  「牡羊座と獅子座」「獅子座と牡羊座」がほぼ同一内容になり、重複コンテンツとして自ら評価を割ります。
  1ペア1URLに集約し、タイトル・h1・description に**両方の並び順と、かな表記**(おひつじ座/しし座)を
  含めて、どちらの語順で検索されても拾えるようにしています。
- 本文は「基本データ / ふたりの空気 / 一緒に何をすると楽しいか / こじれ方 / 4層診断への接続」の5節。
  素材は `ZODIAC`(気質・支配星・エレメント)、`zodiacCompatScore`(エレメント相性)、
  `AISHO_PLAY`(遊び方)から取り、ペアごとに実質2,200〜2,500字。
- 全ページに **「星座だけでは相性は決まらない」→ 4層診断へ** という接続を置いています。
  検索意図に答えたうえで、プロダクトの価値(生年月日まで見ると答えが変わる)に橋を架ける形です。

**九星気学(9ページ)** — `/kyusei/{star}/`

- 「一白水星 性格」「本命星 調べ方」「吉方位」は、四柱推命LPの中に埋もれていて拾えていませんでした。
- 各ページに**九星どうしの相性を9通りぶん**(相生/比和/相剋)展開し、
  五行の関係を `GOGYO_RELATION` から計算しています。
- **立春(2月4日ごろ)が年の変わり目**という、この分野でいちばん検索される躓きポイントを
  全ページのFAQに置きました。

### 3.3 内部リンクの張り方

新しいページは、sitemapに載せるだけでは弱い。実アンカーで繋ぎました(`scripts/link-clusters.mjs`)。

- 全LPのフッターに `/aisho/seiza/` と `/kyusei/` を追加(98ページ)
- **12星座ページ → その星座の相性12本**(検索意図がいちばん近い導線。12×12=144本の実リンク)
- `/aisho/` → 星座相性ハブ、`/shichusuimei/` → 九星ハブ、`/seiza/` → 星座相性ハブ
- トップの Guide リンク列にも2本追加

内部リンク総数 7,883本、リンク切れ0、sitemap 188 URL(旧99)。

## 4. 次に取りに行く検索面(未実装・優先度順)

### 4.1 「◯◯座 今日の運勢」 — 最大の未取得クラスタ ★最優先

「しし座 今日の運勢」系は、占いカテゴリで**毎日検索される最大のボリュームゾーン**です。
いまMYOURISCOPEには受け皿がありません。

**実装の考え方**: 静的サイトなので、GitHub Actions の `schedule` で毎日ビルドします。

```
/seiza/{sign}/today/   … 12ページ、毎日00:05 JSTに再生成してコミット
```

- 本文は `dailyVerdict` 相当のロジックを**星座単位に落とした版**で生成する
  (個人の生年月日がないので、太陽星座+その日の月相・干支だけで読む簡易版)。
- 「もっと正確に観るなら生年月日を」で `/#today` に送る。**このクラスタの本当の価値は流入で、
  精度の高い結果はアプリ側にある**、という役割分担を明示する。
- 注意: 中身が薄いまま12ページを毎日更新すると、低品質判定のリスクがあります。
  1ページあたり最低800字、かつ**その日固有の根拠**(今日の日支・月相)を必ず本文に出すこと。

### 4.2 四柱推命の日主・通変星 — 10 + 10ページ

「甲 日主」「偏官 意味」「通変星 一覧」。`NIKKAN_DESC` と `TSUHENSEI` に
gloss/day/month テキストが既にあるので、タロット78枚と同じ手法で生成できます。
競合が少なく、四柱推命に本気の層(=滞在が長く再訪する層)が来ます。

- `/shichusuimei/nikkan/{kan}/` 10本 — 日主ごとの気質・相性・日運の出方
- `/shichusuimei/tsuhensei/{star}/` 10本 — 通変星の意味・出たときの過ごし方

### 4.3 誕生日占い — 366ページ

「3月14日生まれ 性格」。ボリュームは大きいが、366ページを薄い内容で作ると
サイト全体の評価を下げます。**やるなら**、星座+その日の十干+九星の3つを実計算して
1ページ1,000字以上を確保できることを確認してから。優先度は 4.1 / 4.2 の後。

### 4.4 暦イベント — 数ページで効率が良い

「2026 新月 満月 カレンダー」「水星逆行 2026 いつ」。
`moonPhaseToday()` と `isMercuryRetrograde()` が既にあるので、年間表を生成できます。
ページ数は少ないのに検索は毎月立つ、費用対効果の良い面です。

- `/koyomi/shingetsu-mangetsu/` — 年間の新月・満月一覧(月ごとの過ごし方つき)
- `/koyomi/suisei-gyakko/` — 水星逆行の期間一覧

### 4.5 質の改善(面を増やさない打ち手)

- **タイトルの見直し**: Search Console で「表示回数は多いがCTRが低い」ページを特定し、
  タイトル先頭32文字に検索語をそのまま置く。とくに `/tarot/cards/` 78本は要点検。
- **かな表記の網羅**: 「おひつじ座」「牡羊座」両方で検索されます。相性ページには入れましたが、
  `/seiza/{sign}/` の本文にも、かな表記を自然な形で増やす余地があります。
- **FAQPage構造化データ**: 既に全LPに入っています。`faq_open` の計測で
  「実際に開かれている質問」がわかるので、開かれない質問は検索意図とずれています。差し替える。

## 6. 関連するスクリプト
